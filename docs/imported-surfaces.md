# Imported triangle surfaces

Import an OBJ or STL from **Surface → Import OBJ / STL**. Choose the coordinate unit before importing: millimeters, centimeters, meters or inches. The default selection is millimeters; it is a user declaration, not a unit inferred from the file. Geometry stays in the browser. Parsing and connectivity analysis use cancellable local workers. The current surface remains visible until a successful import is accepted; errors, cancellation and obsolete responses preserve it. Import is one undoable project edit.

Imported surfaces currently support viewing, triangle selection, geometric/connectivity inspection, viewport PNG and project JSON. Pattern generation and direction drawing require a verified surface mapping and are unavailable on imported meshes. The original support-mesh triangles are not presented as newly generated retopology. Return to an analytic surface or load a learning example to generate networks.

## Coordinates and identity

Each input coordinate is multiplied by the declared unit scale (mm: 0.001, cm: 0.01, m: 1, in: 0.0254 meters per source unit). The bounding-box midpoint of all declared vertices is then subtracted, followed by a residual centering pass to handle large coordinate offsets. Axes, handedness and shape scale are preserved. The original midpoint is stored as `source.centerMeters`; add it to centered coordinates to recover the original position in meters to floating-point precision. Large offset-to-extent ratios produce an explicit precision note; the import does not recover precision already lost when parsing or scaling source numbers. There is no size normalization or approximate mesh healing.

OBJ retains its declared position-index identities, including distinct vertices at equal coordinates. STL lists triangle corners without a shared index structure; the importer shares vertices only for exactly equal parsed coordinate triples, with signed zero canonicalized. Near-equal positions remain distinct. This indexing choice affects apparent boundaries, components and Euler counts and is recorded in the project. Coincident geometric crossings do not create adjacency.

## Supported file subset

- **OBJ:** UTF-8 polygonal `v` and `f` records; positive and negative position indices resolved at the face declaration; `v/vt/vn` face syntax accepted while UVs, normals, groups and materials are ignored. Position vertices require three coordinates and optionally w=1. Planar simple polygons of 3–256 vertices are triangulated with preserved winding. Relative planarity/intersection tolerance is 1e-10 against the polygon extent. Nonplanar, touching, self-crossing or ambiguous polygon boundaries are rejected. Forward position references, line/point/freeform elements, vertex colors, non-unit homogeneous weights and line continuations are outside this subset. ASCII spaces and tabs delimit semantic tokens; ambiguous embedded carriage returns and Unicode line separators are rejected. Continuations are rejected on ignored statements too. External material and texture files are never loaded.
- **ASCII STL:** strict line-based `solid` / `facet normal` / `outer loop` / three `vertex` records / `endloop` / `endfacet` / `endsolid` grammar, with one solid. Coordinates and supplied normals must be finite; normals do not determine triangle winding. UTF-8 text only.
- **Binary STL:** exact 84 + 50 × facet-count byte layout, little-endian numbers, finite coordinates and normals. The count/length test takes precedence over a header beginning with `solid`. Color/attribute bytes are ignored. Truncation and inconsistent layout are rejected.

These are declared subsets, not complete format compatibility. Format references: the Library of Congress describes [OBJ polygon/vertex records](https://www.loc.gov/preservation/digital/formats/fdd/fdd000507.shtml), the [STL family](https://www.loc.gov/preservation/digital/formats/fdd/fdd000504.shtml), [ASCII STL](https://www.loc.gov/preservation/digital/formats/fdd/fdd000506.shtml), and [binary STL](https://www.loc.gov/preservation/digital/formats/fdd/fdd000505.shtml). Its binary documentation gives the facet count, numeric layout and 50-byte records; its descriptions do not validate an individual mesh or this implementation. Accessed November 6, 2026.

## Measurements and their limits

The inspector reports vertices, triangles, unique indexed edges, used-vertex components, boundary edges, non-manifold edge incidence, invalid vertex links, inconsistent shared-edge winding, duplicate indexed triangles, degenerate triangles and isolated vertices. Components use the triangle-edge graph on used vertices; isolated declared vertices are reported separately. Repeated-index collapsed triangles are retained as source defects but excluded from incidence edges, vertex links, orientation checks and incidence F. Raw used vertices remain in the component graph, including any resulting singletons. Euler is all declared V − unique incidence E + incidence F, including isolated vertices; the inspector reports raw, incidence and collapsed triangle counts separately. Three distinct indices with collinear geometry remain in incidence and are flagged geometrically degenerate. It is not a genus inference.

Area is the sum of unsigned triangle areas, including duplicates or overlaps. Degeneracy means cross-product triangle area at or below maximum bounding-box extent² × 1e-14 m². The bounding box includes unused declared vertices, so distant unused vertices can affect this numerical classification. A mesh with no triangle above this threshold is rejected; other defects remain visible for inspection without repair. Polygon planarity and this area classification are numerical thresholds, not exact predicates.

Algebraic signed volume uses a compensated sum of origin-tetrahedron determinants divided by six. It is shown only if indexed incidence is closed, vertex links pass, shared-edge winding is consistent, and there are no duplicate or degenerate triangles. Its sign follows winding, and disconnected shells can cancel. No global triangle intersection/overlap test, enclosed-solid certificate or physical material-volume claim is made. Selection retains a post-triangulation imported triangle index (not the OBJ face-record ordinal) and shows its actual stored vertices; rendering and ray picking use GPU/display precision.

## Bounds and saving

Files are limited to 20 MiB, 200,000 declared/welded vertices and 200,000 triangles. Text lines are limited to 65,536 characters; polygons to 256 vertices. OBJ polygon triangulation also has a cumulative 5,000,000-work-unit budget counting executed orientation predicates and Newell, planarity, edge-length, area and ear-loop steps; excessive cases are rejected explicitly and can be triangulated upstream. Source coordinates after unit conversion must be within ±1e9 m. The maximum centered bounding-box extent must be within [1e-6, 1000] m. Saved centered coordinates are checked against their bounding-box midpoint with tolerance max(1e-12 m, extent × 1e-10). These are implementation bounds and tolerances.

Project JSON retains the centered indexed mesh, unit declaration, original offset and import notes. Notes are limited to known importer wording, and source fields remain unauthenticated provenance; they do not prove the origin of a saved file. STL payloads cannot contain vertices unused by every raw triangle. Loaded arrays and metadata are bounded and revalidated. Serialized diagnostic reports are not trusted; analysis is recomputed in a worker. Imported projects cannot contain generated graphs or analytic guide attachments. Method records label mesh inspection explicitly and do not attribute a quadrangulation or pattern operator. Older analytic projects remain readable. History shares immutable mesh objects and bounds the retained geometry budget. Autosave is best effort; download project JSON for durable storage.
