# Knitting Topology

A static surface pattern and topology laboratory by Nijat Mahamaliyev / Tailored Materiality Research. The workspace follows the dark monochrome visual language of Knitting Pixel Art Editor. Computation runs locally in the browser without a backend server.

## Run locally

Use a current supported Node.js release (developed with Node 26.11.1), then:

```sh
npm ci
npm run dev
```

Open the printed URL ending in **`/KnittingTopology/`**. To check the production build:

```sh
npm run check
npm run preview
```

`npm run check` runs type checking, numerical/project tests, and the static production build. The browser suite is separate:

```sh
npm run test:browser
```

The browser configuration uses installed Google Chrome on macOS, with isolated contexts and a software WebGL fallback. Set `KNITTING_CHROME` to another Chrome/Chromium executable and `KNITTING_BASE_URL` to a running preview if needed. `KNITTING_GPU=hardware` removes the software override. See [verification notes](docs/verification.md) for actual coverage and limits.

## Explore

1. Choose a **plane, cube, sphere, or saddle**. Import OBJ/STL for [surface inspection](docs/imported-surfaces.md) with an explicit unit declaration. OBJ files with a suitable [supplied rectangular UV chart](docs/mapped-surfaces.md) support network generation; other imports remain inspection-only. Dimensions and spacing are displayed in millimeters; scientific state uses meters.
2. Choose **Surface patch network** for regular, inset, alternating or nested control topology. Set target spacing, or edit compatible strip subdivisions in the Topology inspector.
3. Use **Draw guide** to sketch soft direction preferences on the surface. Orbiting the camera does not move attached strokes. **Field orientation** defines the background tangent cross-field.
4. Press **Generate / Regenerate** (G). Generation is explicit and cancellable; obsolete results cannot replace newer edits. The previous accepted result stays visible while computing on the same surface.
5. Inspect nodes/cells, components, seams, valence, spacing, and method provenance. Try **quad, dual, ambo, kis, gyro, and diagonal** graph families.
6. Capture up to four session variants in **Compare**. Check feature budgets as well as geometry before interpreting differences. A capture also keeps the current knit program: its card shows the key, size, structures, transfers, checks and export blockers, and, when the size matches variant 1, how many cells differ in operation meaning. Restore or save any captured variant.
7. Save **project JSON** to retain geometry, guides, graph identities, coarse topology/strips, settings, diagnostics, seed, and provenance. Undo/redo restores project semantics within the session; the undo stack is not exported. Local autosave is best effort; download JSON for a durable record. If a network exceeds local cache quota, the latest inputs are retained for regeneration. Invalid cached records are preserved for recovery.
8. Open **Learn** to explore 13 topics with actual construction diagrams, assumptions, source relationships and controlled examples. Browsing leaves your project unchanged; loading an example is undoable and requires explicit generation. Copy qualified method descriptions or download BibTeX/CSL references. See [methods and attribution](docs/methods.md).
9. On cube or sphere, use **04 Cuts and seams** to apply a preset or edit source edges, validate one disk and export paired seam JSON. See [closed-surface cut preparation](docs/closed-surface-cuts.md). A cube cut made only of whole crease lines, or a sphere cut running from pole to pole, can then be knitted in **05 Knit program**; see [closed-surface knitting](docs/closed-surface-knitting.md). On open surfaces, open **04 Knit program**. Use **Shape** on a plane, saddle or supplied rectangular OBJ chart: enter your measured swatch, choose the start edge, then Generate shape. Inspect courses and shaping marks beside the bitmap; unresolved required shaping blocks operation exports. See [shaping construction and limits](docs/knit-shaping.md). Use **Network** or **Shape and network** to translate the accepted network into a design-level bitmap in the Knit Grammar convention of Knitting Pixel Art Editor. Measured modes share one reference mapping; typed network dimensions use a rectangular chart grid. Create immutable user structures in the tile editor. See [network mapping and limits](docs/knit-network-mapping.md). Assign structures to cells (uniform, side count, alternating, coarse cell or per cell), edge lines and node marks. Automatic transfers are added where a needle changes bed. Show the program beside the surface: pointing at a loop marks it in 3D, and selecting a cell, edge or node outlines its loops. The Knit tab lists Knit Grammar's checks and exports the BMP, the Knit Grammar JSON, a report and the measurement table. Lab rules still to confirm are visible settings. Pick the colour key under Key; make a custom copy or read a key from a Knit Grammar pattern JSON in the Knit tab.

Missing knit inputs are listed beside Generate in an amber panel. Its repair buttons open the relevant controls and focus missing measurements; numerical failures appear separately in red. See [generation requirements and recovery](docs/knit-interaction.md).

The **Knit** and **Learn** tabs include **KnitCrete workflow · understand and cite**. Step through source methods, implemented adaptations and remaining capabilities, inspect the source settings, and download the thesis citation or qualified method wording. Under a measurement, open **Calibration context (optional)** to record its state, machine settings and protocol in your own units. See the [thesis workflow audit and development order](docs/popescu-workflow-audit.md).

The **N-sided patch laboratory** is a separate plane construction with hard subdivision counts. It contains a verified, intentionally incomplete template set. Useful examples: four sides `[10, 6, 10, 6]`; three, five or six sides with all counts `6`; the triangular-boundary single-quad case `[2,1,1]`. Unsupported combinations report an error and retain the previous accepted graph. See the exact [core method contract](src/core/README.md).

Exports: meter-coordinate OBJ polygon mesh, XY-projection SVG, viewport PNG, diagnostic CSV, full project JSON, selected method references in BibTeX, and a method record in JSON. Saved projects include a supplementary method record describing the accepted graph separately from pending settings. SVG is a projection, not a surface flattening or fabrication pattern. OBJ faces use straight chords and do not retain every project semantic.

For the bounded plane channel/pocket presets, see [recipe setup, inspection and limits](docs/knit-recipes.md).

## Scientific scope

This is a **geometric cell-network explorer** with a **design-level knit program** export. The topology network is geometric; it is not a stitch graph. The knit program translates it into a Knit Grammar bitmap for the lab's Steiger software, where the final operations and machine code are produced. It does not claim machine-ready files, knittability, achieved shape, material calibration, structural capacity, or fabrication validation.

- **Takayama, Panozzo and Sorkine-Hornung (2014), _Pattern-Based Quadrangulation for N-Sided Patches_:** the implemented bounded templates are independently written and explicitly smaller than the complete paper construction. There is no general 2–6-sided coverage or global minimal-singularity guarantee.
- **Oval et al. (2018), _Topology Finding of Structural Patterns_:** coarse connectivity, strip density, pattern mapping, and embedding are distinct stages. Current presets are project-authored templates; they do not reproduce the paper's medial-axis initialization, complete A–K grammar, poles, or structural analysis.
- Closed cubical/spherical atlases, soft guide fitting, feature-preserving cube transformations, and open-boundary operator rules are documented project extensions.
- Target spacing and guide alignment are measured preferences. Integer rounding, atlas distortion and transformations change achieved edge lengths. Local validity checks do not certify the absence of all global intersections.
- **Knit program:** one pixel is one needle and one row is one carriage pass (bottom row = pass 1). Each colour is an operation from a 4.S52 class key for one or two yarn guides (Colour key from Computational Textiles (MIT 4.S52/6.S895, Spring 2026), Mariana Popescu), or from a custom copy of one. Custom keys are edited here or read from a Knit Grammar pattern JSON, and operations are matched by what they do, not by colour. Scale comes from swatch measurements you enter, and unmeasured structures use jersey values, flagged. Shaped output is a geometric prediction from those measurements and is not verified until knitted. Lab rules that are not yet confirmed (first pass direction, transfer timing) are visible settings. Checks are warnings and do not certify knittability.

Shape mode supports the plane, saddle and supplied rectangular OBJ charts, with a selectable start edge and user-measured loop dimensions. Course and loop generation is adapted from Popescu (2019), §§5.2 and 6.2; distance-field construction, monotone alignment and needle placement are project adaptations. Short rows, increases and decreases are recorded with surface provenance. Results with unresolved required shaping steps remain inspectable, but BMP and Knit Grammar JSON export is blocked. These geometric predictions are not physical simulations or machine-ready programs. The two-guide key works in every mode. Short rows hold both yarns; shaping that needs a transfer is reported as unresolved and blocks export, because the key has no transfer operation.

The thesis workflow guide distinguishes source methods, project adaptations and missing capabilities. Swatch records can include measurement state, machine, knit point, yarn tension, knitting speed and test protocol. These are user-entered calibration context, not machine instructions or a material model. Existing records without this context remain readable and are labelled unspecified. Native symbol libraries, arbitrary patch boundaries and further feature recipe families remain separate development work.

Measured course layouts keep their knit graph stages, following the thesis workflow (§6.3, pp. 105–112): the courses stage (contour samples joined into courses) and the loops stage (loops and their parent links). They are saved in the project and as separate stage files, and are marked stale when their inputs change. The courses stage can be edited on the surface, as in the thesis (§6.3.2, pp. 111–112): with her method, its vertices and links; with the project method, its course polylines and short-row turns. Each edit is recorded, and the layout is rebuilt and checked after it; rule violations block export as for generated stages. An edited stage is never replaced without the user's choice. Loops-stage editing is not implemented yet. On open surfaces a second, selectable course method reconstructs the thesis's written connection rules (§§6.2.2–6.2.3): nearest candidates on adjacent contours, leaf ends first, the most perpendicular link with an angle-tolerance tie-break, and division of each segment between end vertices. It is built from the thesis text, not from her compas_knit software; where the text is silent, the project's choices are documented. Its stages are checked against the thesis connection rules, and every stage for duplicates and consistent parent links; violations block BMP and Knit Grammar JSON export. Spacing weft/warp and Refinement are not implemented.

Computational patches follow the thesis workflow (§6.3.2, pp. 109–110). In shape mode on open surfaces, split lines at constant chart u or v divide the chart into a grid of rectangular patches. As in the thesis, each patch has its own knitting direction, loop dimensions (from its fill structure's swatch) and course method, and its own saved, editable knit graph stages. The thesis splits the geometry by hand and develops no subdivision strategy; the grid of full-length split lines is a project restriction. Each shared edge is knitted through or a seam, chosen by clicking it on the surface; new edges start knitted through. Patches linked by knitted-through edges form one piece of any connected shape, with one bitmap. The thesis combines patch patterns into one pattern but describes no algorithm, so the join is a project construction. Side by side, the courses that reach the shared edge are paired in order along it, and an unpaired course becomes a short row turning at the edge. Stacked, the upper patch's first course is linked to the course below by the needle planner. Patches in one piece must share a start edge. Their fills may differ, as the thesis allows; the join between loop sizes is not validated physically. A Popescu-method patch keeps its loop connections inside the patch. The joined loop graph is rebuilt at each generation, not saved, and its checks block export. Where part of a piece ends at an edge inside the chart, its needles stop: the colour key has no cast-off, so each stop is reported, to be cast off in the lab software or held to the end, and export is allowed. A piece with separate arms in one band (a U, an arch or a ring) needs a yarn jump between them, which blocks export. A seam between two patches of the same piece also blocks export. A seam map lists the loops or course ends along both sides of every seam, paired by position along the edge as sewing guidance (project rule). Count and length differences are reported and do not block export. Topology network patches are never used as knit patches.

Feature zones mark where features go, as in the thesis workflow (§6.3.2, p. 112; §6.4.1, pp. 113–114). On open surfaces, in every mode, a zone is drawn on the surface as a stroke with a width in millimetres or as a closed region, and stored in chart coordinates, so it survives regeneration. Its kind comes from the thesis list (channel, opening, pocket, inlay or insert, material region, colour pattern), and it has a name and a colour. A loop belongs to a region when its chart position lies inside it, and to a stroke when its centre lies within half the width of the stroke's path on the surface (project rule). The bitmap preview shows the marked cells, and clicking a marked cell selects its zone. Zones alone are intent only: they change no operation. An explicitly assigned feature recipe can change operations in that zone. A zone map JSON lists each zone and its cells. A marked BMP shows the operation bitmap with each zone's cells in the zone's colour, for filling the zones with feature clusters in the lab software, as in the thesis (Fig. 6.19); it is not a Knit Grammar program, and zone colours must differ from the key's colours. Zones may overlap; the zone lower in the list is drawn on top. The first optional recipes implement the bounded channel and pocket constructions described below.

Every knit program is also written as an operation sequence: the carriage passes in knitting order, machine-neutral, after the thesis workflow, in which symbols become operations that are simulated before the machine file is written (§6.4.1, pp. 113–114). Each needle in a pass has a symbol, an ordered list of steps (Fig. 6.18): yarn-fed steps (knit or tuck by a yarn guide on the front or back bed) and yarn-free steps (transfers straight across or diagonal, the class key's same-bed moves, and drops, as in Fig. 7.34j–k). Clusters of symbols can be repeated over cells. A pass's racking follows from its diagonal transfers (project sign convention, not a machine value). The class-key bitmap converts to a sequence without loss; a sequence converts back only when the key has an operation for every symbol, otherwise the conversion is refused and export is blocked. An executor follows the sequence symbolically, with each pass's yarn-fed steps before its yarn-free steps (project convention). It tracks the live loops on every needle of both beds and where each yarn guide stopped. It reports stitches on empty needles, transfers from empty needles or onto occupied ones, drops of live loops, loops left on the needles after the last pass, yarn-guide jumps, and guides used in the same direction twice in a row, which would have to travel back without knitting. It is not a machine simulation. Steps the sequence cannot perform block export (project rule): a transfer or move that takes a loop off the program's needles, and transfers in one pass that need different rackings. In shape mode the shaping check still blocks as before. An operation sequence JSON lists the symbols, the passes, the findings and the blockers; it can be downloaded while export is blocked, and it is not a machine file. Channel and pocket recipes produce guide-swap clusters; no recipe yet produces drops or diagonal transfers.

Optional channel and pocket recipes apply locally to rectangular feature zones on an unpatched, constant-width, unshaped plane program, with two yarn guides knitting one stitch on each bed at every position. The body keeps the two layers separate; join bands change which guide knits each bed, following the layer-connection principles in Popescu (2019), §5.5, pp. 90–91, Figs. 5.26–5.27. The finite presets, band rules and validation are project constructions, not copied native symbols. A channel runs along needles or passes and its two access ends must reach opposite panel boundaries. A pocket has one selected boundary mouth (left, right, first-pass or last-pass side) and three joined sides. Access is between the layers at a panel boundary; no hole is cut through a face. Join bands are inside the zone; the clear body must span at least two needles and two passes (project limit). The preview and report identify body, joins and access edges. Applied recipe footprints must not overlap; strokes, curved surfaces, computational patches, shaping and incompatible base operations are refused. An unresolved assigned recipe blocks BMP and Knit Grammar JSON export; other cells stay unchanged. The actual expanded sequence is retained for inspection and export, including when conversion to the selected colour key fails. Symbolic checks inspect layer-parent continuity and cross-bed yarn paths at joins and openings. They do not establish an impermeable seam, usable channel dimensions, knittability or achieved shape. Cast-on, finishing and native machine scheduling remain lab work.

Network and combined modes support the plane, saddle and supplied rectangular OBJ charts. Measured layouts reuse one course/loop mapping across modes; network-only output fills unused bitmap cells and reports the added passes. Typed network layouts use a rectangular UV grid and do not predict physical shape. Network assignments use original-chart cell containment and a local loop-scale metric for edge and node marks; these are sampled project mappings, not geodesic or material guarantees. User structure tiles are saved as bounded, immutable copies using known key operations; new copies do not inherit measurements. Required shaping or operation conflicts in combined mode block BMP and Knit Grammar JSON export.

Cube and sphere cut planning works on the accepted closed geometric cell network. Validation checks source manifold incidence and orientation, a connected cut tree, duplicated vertex fans, and a connected disk with one boundary and Euler characteristic 1. Seam-map JSON pairs the two copies of every cut edge with source identities and boundary directions. The cut step itself is topological. On a cube, a cut made only of whole crease lines can then be knitted from its exact flat net in 05 Knit program; the knit report lists the loops on both sides of every seam. On a sphere, a cut that runs from pole to pole and descends at every point can be knitted with pole-to-pole courses and short rows. Other cuts do not produce bitmaps. No sewing sequence is given, and paired seams may branch.

An optional shared-reference two-layer check is available for two-guide Shape and Shape-and-network programs on unpatched open surfaces. Both logical fabric layers use the existing reference geometry, with separate loop IDs and parent histories; physical needle bed and logical layer are distinct. The check compares the actual operation sequence with each layer's expected parents and records missing, extra or wrong-layer arrivals. When enabled, unsupported inputs or failed layer histories block BMP and Knit Grammar JSON export; the graph and diagnostics remain inspectable. A layer-graph JSON and report preserve the expected and actual histories. A separate core checker validates explicit candidate transfer phases on a declared logical needle grid, moving whole loop stacks with one project-convention racking per phase and ordered arrivals between phases. A phase cannot reuse a source or use a destination as another source; empty sources and off-grid transfers are refused. This milestone includes analytic examples, not an automatic planner or a phase-authoring interface. It introduces no machine specifications, additional workspace, physical layer thickness or fabrication instructions. Existing transfer restrictions remain in force, and curved channel/pocket recipes are not enabled by this foundation alone.

## GitHub Pages

The Vite base is **`/KnittingTopology/`**. If the repository name changes, update `base` in `vite.config.ts`. Assets, bundled fonts, and the ES-module worker are served below that path. The application uses no server routes.

A **manual-only** Pages workflow is prepared at `.github/workflows/pages.yml`. Select **Settings → Pages → GitHub Actions**, then run **Deploy Knitting Topology** from the Actions tab. The workflow has no push trigger. Configuration follows the [official Vite Pages guidance](https://vite.dev/guide/static-deploy).

## Structure

```text
src/core/       analytic surfaces, coarse strips, templates, graph transforms, diagnostics
src/viewer/     Three.js display, picking, surface-attached drawing, camera controls
src/app/        React workspace, immutable project history, validated serialization
src/workers/    revision-tagged background generation and progress protocol
src/adapters/   explicit geometry/projection/project exports
src/learning/   method lessons, construction diagrams and citation registry
src/import/     bounded mesh parsing, local diagnostics and import interface
src/knit/       knit program: keys, structures, shaping, surface mapping, cuts, comparison and file exports
tests/         numerical, project and isolated browser verification
research/      primary-source register and scientific references
```

Automatic mapping of arbitrary imported surfaces, direct graph grammar editing, pseudo-quads/poles, calibrated mechanics, yarn-level simulation, and machine code generation are future work. The contracts preserve a boundary for them without claiming they are implemented.
